# «Пульс Тур» — план превращения календаря в платформу для турфирм

> Цель: турфирма из офиса ведёт расписание тура (вылеты, трансферы, экскурсии, заселение),
> турист открывает сайт или приложение, видит **своё** расписание и заранее получает уведомления —
> в том числе об изменениях.

---

## 0. Что уже есть и что из этого переиспользуем

| Есть сейчас (`index.html`, `sw2.js`) | Как пригодится |
|---|---|
| PWA: манифест, service worker, установка на главный экран | Основа приложения туриста — почти без изменений |
| Красивый календарь (месяц + список дня), темы, акценты | Экран туриста «Моё расписание» |
| Модель события: `title, date, time, duration, allDay, repeat, color, notes, notify` | Расширяем полями для тура (тип, место, таймзона и т.д.) |
| Web Push: VAPID, `/subscribe`, `/sync`, `/test`, `/snooze` на Cloudflare Worker | Основа сервера уведомлений |
| `buildSchedule()` — клиент сам считает, когда слать пуши, и отправляет на `/sync` | **Меняем принцип**: расписание считает сервер (см. ниже) |
| Попапы, звук, вибрация, «Отложить 10 мин» | Оставляем для туриста |

### Главное архитектурное изменение

Сейчас источник правды — `localStorage` в браузере одного человека. Он сам создаёт события и сам
говорит серверу «пришли мне пуш тогда-то».

В туристической версии **источник правды — сервер (база данных турфирмы)**:

```
 Офис турфирмы (admin)  ──►  API + БД  ──►  Планировщик (cron каждую минуту)
                               │                      │
                               ▼                      ▼
            Турист (PWA / приложение)  ◄──  Web Push / Telegram / SMS
            читает расписание, кэширует офлайн
```

Турист **ничего не создаёт** (максимум — личные заметки), он только читает своё расписание
и получает уведомления. Офис меняет время — у всех туристов группы обновляется расписание
и приходит пуш «Изменение: трансфер перенесён на 07:30».

## 1. Роли и сущности

### Роли
1. **Владелец платформы** (вы) — подключает турфирмы, тарифы.
2. **Турфирма (агентство)** — арендатор платформы (multi-tenant): у каждой свои туры и туристы.
3. **Менеджер турфирмы** — заходит в админку, ведёт туры и группы.
4. **Гид / сопровождающий** (опционально) — видит группу, может отправить срочное сообщение.
5. **Турист** — смотрит расписание, получает уведомления. **Без регистрации и паролей.**

### Сущности (модель данных)

```
agencies        id, name, logo_url, brand_color, contact_phone, timezone_default, plan, created_at
staff           id, agency_id, email, password_hash | magic-link, role (owner|manager|guide), name
tours           id, agency_id, title, description, cover_url           ← шаблон тура («Турция 7 ночей»)
groups          id, agency_id, tour_id, title, start_date, end_date,   ← конкретный заезд/группа
                join_code (короткий, напр. K7QX-2M), guide_name, guide_phone, status
events          id, group_id, type, title, starts_at_utc, ends_at_utc, tz (IANA, напр. Europe/Istanbul),
                all_day, location_name, address, lat, lng, meeting_point, notes, what_to_bring,
                flight_no, airport_from, airport_to, terminal, gate,
                leads_min (JSON, напр. [1440,120,30]), audience ('all' | список participant_id),
                version, updated_at, cancelled
participants    id, group_id, display_name (можно только имя), access_token (секрет в ссылке),
                lang, created_at, last_seen_at
channels        id, participant_id, kind (webpush|telegram|sms|fcm|apns), payload (JSON подписки/chat_id/телефон),
                active, created_at
notifications   id, event_id, participant_id, kind (reminder|change|cancel|broadcast),
                fire_at_utc, status (pending|sent|failed|skipped), sent_at, error
```

Ключевые решения:
- **Группа = отдельный заезд.** Тур «Стамбул 5 дней» — шаблон; группа «Стамбул 12–17 мая» — копия с датами.
  Менеджер создаёт группу из шаблона, и события копируются со сдвигом дат. Это экономит менеджеру часы.
- **`audience`** у события: большинство событий для всей группы, но вылет у половины группы может быть
  другим рейсом, а экскурсия — платной опцией не для всех.
- **`version` + `updated_at`** — чтобы приложение туриста скачивало только изменения и показывало «обновлено».

## 2. Самое важное: часовые пояса ⚠️

В текущем коде время — «локальное время устройства» (`new Date(Y, M-1, D, h, mi)`).
Для путешествий это **источник реальных ошибок**: турист прилетел в Бангкок, телефон сменил пояс —
и «вылет в 10:00» внезапно показывается не тем временем.

Правила:
1. Каждое событие хранит **момент в UTC** + **IANA-таймзону места события** (`Asia/Bangkok`).
2. Менеджер вводит время «как в билете/программе» — в местном времени места события
   (для вылета — пояс аэропорта вылета, для прилёта — аэропорта прилёта).
3. Туристу показываем время **в поясе места события** и подписываем: «10:00 (по Бангкоку)».
   Если пояс устройства отличается — мелко: «= 06:00 по Москве».
4. Уведомления сервер считает от UTC — они всегда приходят вовремя независимо от телефона.
5. В JS используйте `Intl.DateTimeFormat(…, { timeZone })`; для арифметики — библиотеку
   (`Temporal` полифил или `luxon`/`date-fns-tz`).

## 3. Как турист попадает в своё расписание (без регистрации)

1. Менеджер добавляет туристов в группу (или просто генерирует N мест).
2. Система выдаёт **персональную ссылку + QR-код**:
   `https://pulse.tours/t/AbC9xY…` (длинный секретный `access_token`).
   Плюс общий короткий **код группы** `K7QX-2M` — на случай, если ссылку надо продиктовать.
3. Ссылку отправляют в WhatsApp/Telegram/SMS/e-mail или печатают QR в памятке туриста / на ваучере.
4. Турист открывает ссылку → видит расписание → кнопка **«Включить напоминания»**:
   - Android / ПК — сразу запрос разрешения на пуши;
   - iPhone — инструкция «Поделиться → На экран «Домой»» (см. п. 5), затем разрешение;
   - альтернатива одной кнопкой — **«Получать в Telegram»** (deep link на бота `t.me/PulseTourBot?start=<token>`).
5. Токен сохраняется в `localStorage`, повторный вход не нужен.

Персональный токен лучше общего кода: можно отключить конкретного туриста, слать адресные события,
видеть, кто подключил уведомления (менеджеру полезно: «у 3 человек напоминания не включены — позвоните им»).

## 4. Каналы уведомлений — честно о подводных камнях

| Канал | Плюсы | Минусы |
|---|---|---|
| **Web Push (PWA)** — уже есть | Бесплатно, без магазинов приложений | **iPhone: работает только если сайт добавлен на экран «Домой» (iOS 16.4+)**. Многие туристы этого не сделают. Нужен интернет в момент доставки |
| **Telegram-бот** | Огромный охват в РФ/СНГ, доставка надёжная, ничего устанавливать не надо, бесплатно | Нужен Telegram и интернет |
| **Нативное приложение** (Capacitor-обёртка над тем же сайтом) | **Локальные уведомления работают офлайн** (без роуминга за границей!), надёжные пуши на iOS | Публикация в сторах, особенно App Store из РФ — сложности; RuStore для Android — проще |
| **SMS** | Работает без интернета | Платно, за границей у туриста может не быть связи, только для критичного (вылет) |
| **WhatsApp Business API** | Популярен у туристов из многих стран | Платно, модерация шаблонов, ограничения в РФ |

**Рекомендация:** MVP = **Web Push + Telegram-бот** (оба почти бесплатны и закрывают большинство).
Этап 2 — нативная обёртка на **Capacitor** с локальными уведомлениями (решает «нет интернета за границей»).
SMS — платная опция тарифа только для вылетов.

Отдельно про офлайн: веб-страница **не может** сама поставить уведомление на будущее без сервера
(Notification Triggers API в браузерах так и не появился). Поэтому в PWA: расписание кэшируем
офлайн, а напоминания доставляет сервер. В нативном приложении — при каждой синхронизации
перепланируем локальные уведомления на всё расписание тура.

## 5. Логика уведомлений (сервер)

### Типы
1. **Напоминание** — за `leads_min` до события. Разумные дефолты по типу события:
   - вылет: за 24 ч («завтра вылет, онлайн-регистрация открыта»), за 5 ч («выезд в аэропорт»), за 3 ч;
   - трансфер / сбор группы: за 12 ч (вечером накануне), за 60 и 15 мин;
   - экскурсия: вечером накануне + за 30 мин;
   - питание / свободное время: по желанию, по умолчанию выкл.
2. **Изменение** — сразу при сохранении события в админке, если поменялось время/место:
   «⚠️ Изменение: трансфер в аэропорт перенесён с 08:00 на 07:30. Место сбора: лобби отеля».
   Менеджер видит галочку «Уведомить туристов об изменении» (иногда правят опечатку — уведомлять не надо).
3. **Отмена**.
4. **Рассылка** от менеджера/гида: «Автобус задерживается на 15 минут».
5. **Ежедневная сводка** (опция): в 21:00 по местному времени — «Завтра: 08:00 завтрак, 09:30 экскурсия…».

### Механика (замена текущего `/sync`)
- При создании/изменении события сервер **пересчитывает** строки в `notifications`
  (удаляет pending для этого события, создаёт новые для каждого участника из `audience`).
- **Cron раз в минуту** (Cloudflare Cron Triggers): `SELECT … WHERE status='pending' AND fire_at_utc <= now()`,
  отправляет по всем активным `channels` участника, ставит `sent`/`failed`.
- Подписка вернула 404/410 → `channels.active = false`.
- **Идемпотентность**: ключ `event_id + participant_id + lead + version` — повторная отправка исключена.
- Не слать напоминания, которые «просрочены» больше чем на 10 минут (например, после сбоя).
- Тихие часы: не будить в 03:00 ради «завтра экскурсия» — переносить на 08:00 местного времени
  (кроме вылетов и срочных изменений).

## 6. Админка турфирмы (что должен уметь менеджер)

Отдельная страница `admin.html` (десктоп в первую очередь). Экраны:

1. **Вход** — e-mail + magic link (письмо со ссылкой) или пароль.
2. **Туры (шаблоны)** — список; внутри шаблон программы по дням: «День 1, 14:00 — заселение…».
3. **Группы** — «Создать группу из шаблона» → выбрать дату начала → события создаются автоматически.
4. **Расписание группы** — переиспользуем ваш календарь + вид «таблица/таймлайн» по дням.
   Форма события: тип (иконка), название, дата/время + таймзона (подставляется из группы),
   длительность, место (адрес + ссылка на карту + точка сбора), что взять с собой, для вылета — рейс/терминал,
   кому показывать, когда напоминать.
5. **Туристы** — добавить списком (вставить из Excel), скачать ссылки/QR (PDF-лист для печати),
   статус: «открыл / уведомления включены / Telegram подключён».
6. **Рассылка** — написать сообщение всей группе сейчас.
7. **Журнал уведомлений** — кому что ушло, ошибки доставки.
8. **Настройки агентства** — логотип, цвет (у вас уже есть акцентные цвета — делаем white-label),
   контакты экстренной связи, которые видит турист.

Удобства, которые продают продукт:
- **Импорт** программы из Excel/CSV и экспорт в `.ics` (турист сможет добавить в Google/Apple Календарь).
- **Копирование группы** («следующий заезд — те же события +7 дней»).
- **Предпросмотр «глазами туриста»**.

## 7. Приложение туриста (что видит турист)

Основа — текущий `index.html`, но режим «только чтение»:

- Шапка с логотипом и цветом турфирмы, название тура, даты, **кнопка «Экстренная связь»** (звонок гиду/офису).
- Экран **«Сегодня / Далее»** — главный: ближайшее событие крупно с обратным отсчётом
  («Сбор у автобуса через 1 ч 20 мин, лобби отеля»), ниже — остаток дня.
- Вкладка **«Весь тур»** — список по дням (для тура это удобнее, чем сетка месяца; месяц оставьте как доп. вид).
- Карточка события: время по месту + по дому, адрес с кнопкой «Открыть в картах», что взять, заметки, рейс.
- Метка **«Изменено»** на событиях, которые поменялись после последнего просмотра.
- Настройки: язык, звук, «напоминать за…» (можно добавить свои, но нельзя отключить критичные).
- Личные заметки туриста — хранятся локально (ваш текущий функционал создания событий можно оставить как «Мои планы»).
- **Офлайн**: последнее расписание всегда в кэше (service worker + `localStorage`/IndexedDB),
  пометка «обновлено 2 ч назад».

## 8. Технический стек (рекомендация)

Вы уже на Cloudflare — логично продолжить там для MVP, это почти бесплатно:

| Слой | Технология |
|---|---|
| Фронтенд (турист + админка) | Текущий vanilla JS. Когда админка разрастётся — Vite + Preact/Vue. Хостинг: Cloudflare Pages |
| API | Cloudflare Worker (сейчас уже есть) + роутер **Hono** |
| База | **Cloudflare D1** (SQLite) — сущности из п.1 |
| Планировщик | **Cron Triggers** (каждую минуту) + **Queues** для массовой отправки |
| Web Push | Библиотека для Workers (`@block65/webcrypto-web-push` или аналог) — VAPID у вас уже работает |
| Telegram | Бот через Bot API, webhook на тот же Worker |
| Файлы (логотипы, PDF) | Cloudflare R2 |
| Нативное приложение (этап 2) | **Capacitor** + `@capacitor/local-notifications` + FCM/APNs |

⚠️ **Важная оговорка для работы в РФ:**
- **152-ФЗ** о персональных данных: ПДн граждан РФ (ФИО, телефон) должны первично записываться в базы
  на территории РФ, а турфирма/вы — уведомить Роскомнадзор как оператор ПДн, иметь политику
  конфиденциальности и согласие туриста. Самый простой способ снизить риск в MVP — **не хранить ПДн вообще**:
  турист = анонимный токен + имя по желанию, без телефона и паспортных данных.
- Если планируете хранить ПДн или есть проблемы с доступностью Cloudflare из РФ — тот же дизайн
  переносится на **Yandex Cloud** (Cloud Functions + YDB/Managed PostgreSQL + триггеры-таймеры) или VPS
  в Selectel/Timeweb (Node.js + PostgreSQL + cron). Код на Hono работает и там, и там.
- Проконсультируйтесь с юристом перед коммерческим запуском — это не юридическая консультация.

### API (черновик)

```
# Турист (авторизация по access_token в заголовке)
GET  /api/t/me                      → участник, группа, агентство (бренд, контакты)
GET  /api/t/events?since=<version>  → события (только изменения после версии)
POST /api/t/channels/webpush        → сохранить подписку
DEL  /api/t/channels/:id
GET  /api/t/calendar.ics            → экспорт в календарь

# Telegram
POST /tg/webhook                    → /start <token> привязывает chat_id к участнику

# Админка (сессия/JWT сотрудника, всё фильтруется по agency_id!)
POST /api/auth/magic-link, /api/auth/verify
CRUD /api/tours, /api/groups, /api/groups/:id/events, /api/groups/:id/participants
POST /api/groups/:id/from-template
POST /api/groups/:id/broadcast
GET  /api/groups/:id/participants.pdf   → лист с QR-кодами
GET  /api/notifications?group=…

# Служебное
GET  /vapid                          → уже есть
cron                                 → рассылка pending-уведомлений
```

Безопасность: каждый запрос админки проверяет `agency_id` сотрудника (иначе одна турфирма увидит
туристов другой); токены туристов — длинные случайные (≥ 128 бит); rate-limit на вход по коду группы.

## 9. Структура репозитория

Сейчас всё в одном `index.html` (~730 строк) + два почти одинаковых SW (`sw.js` и `sw2.js`),
а код Cloudflare-воркера в репозитории отсутствует. Предлагаю:

```
/app/            ← PWA туриста (из текущего index.html)
  index.html, app.js, styles.css, sw.js, manifest.json, icons/
/admin/          ← админка турфирмы
  index.html, admin.js, admin.css
/shared/         ← общее: работа с датами/таймзонами, рендер календаря, иконки типов событий
/worker/         ← сервер (перенести сюда текущий воркер!)
  src/index.ts, src/routes/*, src/push.ts, src/telegram.ts, src/cron.ts
  migrations/0001_init.sql
  wrangler.toml
/mobile/         ← (этап 2) Capacitor-проект, использует сборку /app
/docs/
```

Первые шаги по чистке:
1. Перенести код воркера в `/worker` под git (сейчас он, судя по всему, живёт только в Cloudflare).
2. Оставить один service worker (сейчас регистрируется `sw2.js`, `sw.js` — устаревший).
3. Вынести JS и CSS из `index.html` в отдельные файлы.
4. Текущий личный календарь сохранить как есть (ветка/папка `personal/`) — он может остаться отдельным продуктом.

## 10. План работ по этапам

### Этап 0 — подготовка (≈ 1 неделя)
- [ ] Перенести воркер в репозиторий, настроить `wrangler`, деплой из GitHub (Actions или Cloudflare Pages).
- [ ] Разнести `index.html` на файлы, удалить `sw.js`.
- [ ] Поговорить с 2–3 турфирмами: как они сейчас передают программу (Word/WhatsApp?), что болит,
      сколько групп в месяц, нужны ли гиды в системе. **Это важнее кода.**

### Этап 1 — MVP (≈ 4–6 недель)
- [ ] Схема БД в D1 (`agencies, staff, groups, events, participants, channels, notifications`).
- [ ] API для туриста + страница `/t/<token>` в режиме «только чтение» с офлайн-кэшем.

## 11. Модель монетизации (идеи)

- **Подписка на агентство**: бесплатно до N туристов/мес, далее тариф по числу активных туристов.
- **Плата за группу** — понятно небольшим агентствам с редкими турами.
- Платные опции: SMS, white-label приложение в сторе под брендом агентства, интеграция с CRM.

Ценность для турфирмы, которую стоит озвучивать в продаже: меньше опозданий к трансферу,
меньше звонков «во сколько выезд?», мгновенное оповещение об изменениях, «вау-сервис» для туриста.

## 12. С чего начать прямо завтра

1. Залить код воркера в `/worker` этого репозитория.
2. Написать `migrations/0001_init.sql` по модели из п.1 и поднять D1.
3. Сделать endpoint `GET /api/t/events` и страницу туриста, которая рендерит события
   существующим календарём (заменив `store.get('pulse.events')` на загрузку с сервера).
4. Перенести логику `buildSchedule()` с клиента на сервер (cron) — это сердце системы.
5. Вручную (через SQL) завести одну тестовую группу и проверить путь туриста целиком:
   ссылка → расписание → включить пуши → пришло напоминание → менеджер поменял время → пришло «Изменение».

После этого админка — «просто» удобный интерфейс к уже работающей системе.
